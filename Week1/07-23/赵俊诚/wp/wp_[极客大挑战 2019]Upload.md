# [极客大挑战 2019]Upload

## 题目来源

[极客大挑战 2019]Upload

## 题目方向 + 知识点

Web 文件上传、图片马、黑名单绕过、`.phtml` 解析、`<script language=php>` 执行。

## 解题思路

这题打开首页之后，页面就只有一个很明显的上传点，功能是“上传头像”。这种题一般不会把思路藏得太深，所以我第一反应不是去猜别的漏洞，而是先把它当成一道典型的文件上传题来分析。

先看页面表单，可以发现文件会提交到 `upload_file.php`，说明后端单独有上传处理逻辑。接着我去访问了 `/upload/` 目录，结果发现这个目录是可以直接列目录的。这个现象很关键，因为目录一旦开放，我就能直接看到历史上传文件。里面能看到不少比较敏感的名字，比如 `.phtml`、`.php.gif`、`.php7` 之类。这一步其实已经把题目的大方向暴露出来了：服务端对上传文件的限制并不严格，核心考点就是文件上传绕过。

既然已经确认题目方向，接下来要做的就不是盲试后缀，而是考虑怎样构造一个既能通过检测、又能被 PHP 执行的文件。

这题拦 `<?`，所以如果直接上传标准 PHP 木马，大概率会被过滤掉。因此这里我没有用普通写法，而是改用另一种 PHP 代码形式：

```php
<script language=php>echo file_get_contents('/flag');</script>
```

这段代码本身就已经足够完成目标了，因为只要服务端把它按 PHP 解析执行，它就会直接把 `/flag` 的内容读出来。

但是只有代码还不够，上传题通常还会检测是不是图片，所以我又在文件最前面补上了 `GIF89a`，把整个文件伪装成 GIF 图片头。最后实际上传的内容就是：

```php
GIF89a<script language=php>echo file_get_contents('/flag');</script>
```

文件名我命名为：

```text
1.phtml
```

这样构造的思路很清楚：

- `GIF89a` 用来通过基础图片检测；
- `.phtml` 这个后缀在很多 PHP 环境中也会被当成脚本解析；
- `<script language=php>` 不包含 `<?`，可以绕过只针对 PHP 标签的黑名单。

为了验证这条链子确实成立，我把这个文件上传了上去。页面成功回显了上传文件名是 `mine.phtml`，说明文件已经被服务端保存到了 `/upload/` 目录。

既然上传已经成功，最后一步就很直接了，直接访问这个文件：

```text
http://2d93a90fee53c01368cd43b8.http-ctf2.dasctf.com/upload/1.phtml
```

页面返回内容是：

```text
GIF89aCTF2{78b85c77-0c21-44b8-a2a8-d9b5982fdba8}
```

前面的 `GIF89a` 是我自己加上的伪造图片头，后面的内容就是程序执行 `file_get_contents('/flag')` 后读出来的结果。也就是说，这个文件并没有被当成普通静态图片返回，而是真的被服务器按 PHP 执行了。

所以这题的完整链路其实很顺：先从首页定位到上传点，再通过 `/upload/` 目录列表判断题目是上传绕过方向，然后构造带有 `GIF89a` 文件头的 `.phtml` 文件，并使用 `<script language=php>` 绕过对 `<?php` 的拦截，最后访问上传后的文件，直接把 `/flag` 读出来。

## 一、文件上传题常见考点

文件上传题本质上一般就考下面这些东西：

### 1. 前端校验

最常见的就是页面用 JavaScript 限制：

- 只能上传图片
- 只能上传某些后缀
- 文件大小有限制

这种一般不是真正的安全校验，因为前端代码在本地就能改，或者直接不走前端，自己发请求。

### 2. MIME 检测

服务端有时候会检查：

- `image/jpeg`
- `image/png`
- `image/gif`

这种考点本质上是在看服务端是不是只信任请求头里的 `Content-Type`。如果只看这个，就说明校验比较弱。

### 3. 后缀名检测

这是最常见的上传考点。一般分两类：

#### 黑名单

只拦：

- `.php`
- `.asp`
- `.jsp`

这类题常考的是：

- php 别名后缀
- 大小写绕过
- 双写绕过
- 特殊字符绕过

#### 白名单

只允许：

- `.jpg`
- `.png`
- `.gif`

这类题常考的是：

- 00 截断
- 文件包含配合图片马
- 解析漏洞
- 二次渲染

### 4. 文件头检测

有些题不只看后缀，还会看文件头是不是像图片。

例如：

- GIF 文件头
- PNG 文件头
- JPG 文件头

所以很多题里都会在文件前面加上图片头，把文件伪装成图片。

### 5. 图片函数检测

常见函数：

- `getimagesize()`
- `exif_imagetype()`
- `imagecreatefromjpeg()`
- `imagecreatefrompng()`

其中前两个更偏“识别是不是图片”，后面这些更偏“真正把它当图片处理”。  
如果题目用了重建图片的函数，就可能考二次渲染。

### 6. 上传目录解析

有些题不是“能不能上传”，而是“上传后会不会被解析执行”。

这时候重点要看：

- 上传目录里的文件能不能直接访问
- 某些后缀会不会被当成 PHP 执行
- 能不能通过配置文件修改解析规则

### 7. 文件名处理

有些题虽然过滤了后缀，但文件名处理有问题，比如：

- 只检查一次
- 没有循环过滤
- 没有统一大小写
- 对空格、点号、特殊字符处理不一致

很多绕过其实本质上都是文件名规范化问题。

### 8. 二次渲染

这类题本质上是：

1. 你上传了一张图片
2. 服务端重新生成了一张新图片
3. 真正保存的是新图片

所以重点不再是“能不能上传带马图片”，而是“重新生成后马还在不在”。

### 9. 文件包含联动

有些题上传的文件本身并不会直接执行，但如果站里还有文件包含点，就可以把上传的图片马包含进去执行。

这类题一定要记住一句话：

**上传成功不等于直接 getshell，有时只是给后续文件包含做准备。**

## 二、文件上传常见绕过方式

这一部分只整理最常见的几类，不展开太多变种。

### 1. 绕过前端校验

这种最基础，思路就是：

- 禁用 JS
- 直接改前端代码
- 直接抓包重发请求

本质就是：前端限制不是真限制。

### 2. 绕过 MIME 检测

如果服务端只看 `Content-Type`，就可以把它改成允许的图片类型，例如：

- `image/jpeg`
- `image/png`
- `image/gif`

本质就是欺骗服务端的类型声明。

### 3. 黑名单后缀绕过

这是最常见的一类。

#### 常见思路

- 后缀别名
- 大小写绕过
- 双写绕过
- 特殊后缀组合

#### 常见危险后缀

不同环境里常见的包括：

- `.php`
- `.php3`
- `.php4`
- `.php5`
- `.phtml`
- `.php7`

有些题只拦 `.php`，那别的可解析后缀就可能通过。

### 4. 大小写绕过

如果过滤只拦小写，比如只拦 `.php`，那就可能出现：

- `.PHP`
- `.pHp`

本质是开发者没有统一大小写再判断。

### 5. 双写绕过

如果程序只是简单替换一次敏感字符串，就可能出现双写问题。

本质是：

- 程序替换后又拼出了危险后缀
- 过滤逻辑不是完整匹配，而是局部替换

### 6. 空格绕过

有些环境里，文件名末尾空格在某一步会被忽略，导致：

- 检查看到的是一种名字
- 实际保存或解析时又变成另一种名字

这类题重点不在空格本身，而在于“校验和最终解析不一致”。

### 7. 点号绕过

有些题会出现：

- 末尾点号
- 多个点号

同样本质是文件名处理不一致。有的地方把点保留，有的地方会裁掉。

### 8. `::$DATA` 绕过

这个是 Windows 环境里比较典型的一类思路，和 NTFS 的备用数据流有关。  
做题时如果环境是 Windows，就要想到这种可能。

本质上还是：

- 程序看到的文件名
- 文件系统最终处理的文件名

可能不是完全同一个东西。

### 9. `00` 截断

这是经典考点，经常出现在白名单题里。

它的本质是：

- 程序校验时看到的是安全后缀
- 底层处理时在某处被截断
- 最终真正保存成危险文件

不过要注意：

- 不是所有环境都能用
- 现在很多新环境已经修掉了
- GET 和 POST 场景里表现也可能不同

### 10. `.htaccess` 绕过

如果环境支持，并且允许上传配置文件，那么可以通过目录级配置改变某些文件的解析方式。

这类思路的本质不是直接上传木马，而是：

**先改规则，再让普通文件按 PHP 解析。**

所以 `.htaccess` 的危险点非常高，它属于“改变解析器行为”。

### 11. 图片马

图片马就是在图片里插入可利用内容。常见思路是：

- 文件头伪装成图片
- 后面带 PHP 代码

但要注意，图片马不是一定能直接执行，它常见的几种用途是：

- 上传后直接被解析
- 配合文件包含执行
- 配合解析漏洞利用

### 12. 白名单 + 文件包含

有些题只能上传 `.jpg`、`.png`、`.gif`，这时候单靠上传本身不一定能执行。

如果站里还有文件包含点，就可以：

1. 上传图片马
2. 再通过文件包含去加载它

这类题的重点是组合利用，不是单点突破。

### 13. 解析漏洞利用

有些环境里，文件名虽然看起来像图片，但最终仍可能被服务器按脚本处理。

本质还是：

- 应用层认为安全
- 服务器解析层认为危险

所以“解析漏洞”本质上就是解析规则和应用判断不一致。

### 14. 二次渲染绕过

这类题不是简单把 PHP 代码塞进图片就完事，因为服务端会重新生成图片。

所以真正思路是：

- 找渲染后仍能保留的区域
- 或者先拿到渲染后的图片，再对保留下来的结构做进一步利用

这类题比普通上传更考验对图片结构和服务端处理流程的理解。

### 15. 条件竞争

有些题上传后会：

1. 先落盘
2. 再校验
3. 再删除或改名

如果在中间短暂时间里文件能被访问，就可能利用竞争条件。

这类题本质上是：

**危险文件短暂存在，但安全检查和删除不是原子操作。**

## 三、做文件上传题时建议固定分析顺序

以后做题时建议按这个顺序想：

### 1. 先看前端有没有限制

- 只是 JS 还是后端也有校验

### 2. 再看后端校验了什么

- 后缀
- MIME
- 文件头
- 图片函数

### 3. 再看最终保存成什么

- 文件名有没有变
- 路径有没有回显
- 是否能访问上传目录

### 4. 再看会不会被执行

- 哪些后缀能解析
- 上传目录能不能执行脚本
- 有没有配置文件可利用

### 5. 最后考虑是否要联动别的漏洞

- 文件包含
- 解析漏洞
- 二次渲染
- 竞争条件
